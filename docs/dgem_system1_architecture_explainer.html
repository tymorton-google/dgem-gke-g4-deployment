Architecture Blueprint #1 • Cloud Infrastructure & Storage Topology

GKE G4 Inference Runtime, 3-Tier ComputeClass & Stage-2 Vertex AI Cascade

End-to-end Google Cloud deployment topology showing how stateless CPU gateway pods (dgem serve) orchestrate single-pass GPU inference on g4-standard-48 nodes, recover from Spot preemptions in seconds via 3-layer Hyperdisk + /dev/shm caching, and selectively escalate high-entropy slots to Vertex AI gemini-3.5-flash-lite.

Why G4 (RTX PRO 6000 Blackwell) Fits System-1

  • Native SM120 FP4 Tensor Cores: Executes ModelOpt NVFP4 (W4A4) weights natively with 17.53 GiB footprint out of 96 GB GDDR7 VRAM.
  • Massive KV Cache Headroom: Over 78 GiB of free VRAM remains on g4-standard-48 for batched multi-slot retail prompts, SigLIP image tokens, or 2–3× MPS multi-instance sharing.
  • Constant O(1) Step Latency: 4-slot structured decisions complete in 57 ms p50 (67 ms p99).

3-Layer Spot Recovery (87.6 s → 7.91 s)

  • Layer 1 (Secondary Boot Disk): Pre-caches the 20 GB vLLM runtime container image so Spot replacement nodes pull 0 bytes over the network.
  • Layer 2 (Hyperdisk Snapshot / ML): Pre-hydrated VolumeSnapshot streams 17.53 GiB of NVFP4 safetensors into /dev/shm in 7.91 s (11.1x faster than cold GCS).
  • Layer 3 (SM120 JIT Cache): Restores pre-compiled FlashInfer CUDA kernels (jit-cache.tar.gz) in < 1 s, eliminating the 90-second first-request compile stall.

3-Tier ComputeClass Resilience

  • Priority 1 (GKE Spot G4): Primary burst execution tier capturing 60–91% GPU cost savings against On-Demand pricing.
  • Priority 2 (DWS Flex-Start): Dynamic Workload Scheduler provisions fallback G4 capacity (up to 50% discount) during regional Spot tightness.
  • Priority 3 (On-Demand + Active Migration): Guarantees production SLA and automatically migrates back to Spot when capacity frees up.
Architecture Blueprint #2 • G4 Machine Sizing, Multi-Instance GPU Sharing & Pattern 4 Hybrid Scaling

GKE G4 Machine Series Sizing, GPU Sharing (vGPU / MIG / MPS) & Pattern 4 Hybrid Architecture

Because DiffusionGemma 26B-A4B NVFP4 requires only 17.53 GiB of static VRAM weights (~20.5 GiB total with CUDA context and FlashInfer workspace), a single 96 GB NVIDIA RTX PRO 6000 Blackwell GPU on g4-standard-48 has over 75 GiB of spare GDDR7 headroom. Cloud architects can right-size deployments using fractional vGPU shapes (g4-standard-12 / g4-standard-24), maximize single-node throughput via 2–3× NVIDIA MPS, enforce strict hardware SLA isolation via MIG (2g.48gb / 1g.24gb), and combine an Always-On On-Demand Baseline with an Elastic Spot / DWS Flex-Start Burst Pool (Pattern 4).

Use Case A — High-Throughput Batch Catalog Enrichment

2–3× NVIDIA MPS on g4-standard-48 (96 GB)
  • GKE Configuration: --gpu-sharing-strategy=mps,max-shared-clients-per-gpu=2 (or 3) with vLLM continuous batching (gpu-memory-utilization=0.30).
  • 1.4×–1.7× Throughput Boost: Overlaps CPU tokenization, JSON schema building, and logit slicing in Pod A with GPU SM120 FP4 Tensor Core execution in Pod B.
  • 96 GB VRAM Math (3× MPS): 3 × 17.53 GiB = 52.59 GiB weights + 6.6 GiB CUDA context = 59.2 GiB, leaving ~36.8 GiB (~12.2 GiB/pod) for KV cache.

Use Case B — Strict Multi-Tenant / p99 Latency Isolation

Hardware MIG (2g.48gb = 2 Slices or 1g.24gb = 4 Slices)
  • GKE Configuration: Partition g4-standard-48 (96 GB) into 2× 2g.48gb (production recommended) or 4× 1g.24gb hardware instances.
  • Zero Cross-Tenant Jitter: Each MIG slice receives dedicated Streaming Multiprocessors (SMs), L2 cache slices, and GDDR7 memory bandwidth controllers.
  • Workload Separation: Heavy 32-category 2-stage bracket tournaments on Slice 1 never impact 57 ms live search/checkout triage on Slice 2.

Use Case C — Right-Sized Entry / Always-On Baseline

Fractional vGPU (g4-standard-24 48GB or g4-standard-12 24GB)
  • Hypervisor-Level Isolation: Runs 1 dedicated dgem-engine pod per VM on a 48 GB (1/2 GPU) or 24 GB (1/4 GPU) fractional Blackwell slice.
  • 50–75% Lower Baseline Spend: Slashes fixed On-Demand hourly cost for the Pattern 4 24/7 baseline pool while maintaining 0 ms cold start.
  • Simple Operations: No MIG partition management or multi-client MPS memory cap tuning required.
Capacity & GEMM Efficiency Guardrail — Why 5 Instances Cannot Fit on 96 GB & Why 4+ MPS Degrades Throughput:
• Why 5 Instances Fail with Immediate OOM (> 96 GB): Five replicas require 5 × 17.53 GiB = 87.65 GiB in static NVFP4 safetensor weights alone. Adding 5 × 2.5 GiB = 12.50 GiB for per-process CUDA contexts, cuBLAS/FlashInfer SM120 workspaces, and PyTorch allocator reserves pushes total static demand to 100.15 GiB > 96.0 GiB—triggering CUDA out of memory before allocating a single KV cache token.
• Why 2–3× MPS Outperforms 4× MPS on 1 GPU: Running 4 MPS instances duplicates static weights 4 times (70.12 GiB), sacrificing 17.53–35.06 GiB of dynamic KV cache headroom and causing L2 cache thrashing across 4 concurrent weight streams. 1 pod with vLLM continuous batching (MAX_NUM_SEQS=16..32) or 2–3× MPS replicas is the empirical throughput sweet spot.
Recommended Production Topology • Pattern 4 Hybrid Scaling

Architectural Pattern 4: Always-On On-Demand Baseline (dgem-engine-baseline) + Elastic Spot / DWS Burst (dgem-engine-burst)

Rather than choosing between pure On-Demand cost and pure Spot preemption risk, Pattern 4 places two Kubernetes Deployments behind a single unified Service (dgem-engine:8080, selector app: dgem-engine): an Always-On On-Demand Baseline that guarantees 100% availability with 0 ms cold start, and an HPA-driven Elastic Burst Pool that scales out onto discounted Spot G4 (60–91% off) and DWS Flex-Start G4 (up to 50% off) nodes with 7.91 s 3-layer fast-start snapshots.

Architecture Blueprint #3 • Algorithmic & Mathematical Mechanics

How the System-1 Discrete Diffusion Engine (DiffusionGemma 26B-A4B NVFP4) Works

Unlike autoregressive LLMs that decode one token at a time (O(N) sequential forward passes) and suffer from poorly calibrated verbalized confidence, DiffusionGemma treats structured multi-slot decision-making as a single-pass bidirectional denoising problem (O(1) forward pass) over a fixed 128-token canvas, yielding exact per-slot probability distributions in 57 ms.
